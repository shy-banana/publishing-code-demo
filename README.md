# 应用与菜单权限验收示例

本分支在旧测试库 `main` 上创建新的双菜单验收应用，不恢复已退役应用或旧记录，不修改 `main` 的历史版本。只填写测试内容。

## 两个菜单

| 菜单 | 页面 | 受保护接口 |
| --- | --- | --- |
| 验收登记 `checks` | `/checks` | `GET/POST /api/checks` |
| 汇总查看 `reports` | `/reports` | `GET /api/reports` |

前端从网关 `GET /_platform/permissions` 读取当前获准菜单。没有菜单权的页面、旧链接和关联 API 均拒绝；请求返回拒绝或 503 后清除页面上已加载的列表、汇总和菜单。根页面、`index.html` 和静态资源仅是应用成员的公共壳，业务接口没有公共放行。

**此验收应用自己的数据规则：员工仅能登记、查看和汇总本人创建的记录。** 创建人只取网关验证后注入的 `sub`，不接受浏览器提交的 `createdBy`、`sub` 或其他范围。查询始终按 `created_by` 参数化过滤；平台菜单负责人也不自动获得全员业务数据。这只是本例的验收规则，不规定其他应用采用相同规则。

## 平台运行契约

- 保持 Node 动态运行：`node server.mjs`、端口 `3000`、内部 `/readyz`、`database/001-initial.sql`、`nativeOidc:false`。生产运行依赖仍只有原来的固定版 `pg`。
- `MENU_APP_ID` 是平台应用 UUID，`MENU_ACCESS_CONFIG_PATH` 指向平台只读挂载的 `/run/menu-policy/menu-access.json`，目录 `0700`、文件 `0600`、属主 UID `1000`。没有菜单配置不启动；每个请求重新校验当前策略，并以 `expectedCatalog` 绑定本版本 `banana-permissions.json`。
- `APP_ORIGIN`、`DATABASE_URL`、`PG_CA_CERT_PATH` 由平台注入。数据库继续验证 TLS 及证书。初始 SQL 仅适用于本次新应用的新库，不是旧库升级脚本。
- 后端只使用网关清洗后注入的 `x-banana-user-sub`、`x-banana-corp-id`、`x-banana-wecom-userid` 三项身份。**正式部署必须禁止直连 runtime，仅允许网关通过私有网络访问。** 这些请求头不是独立的身份凭据，开放 runtime 会破坏该信任边界。
- 员工停用由正式网关逐请求复验当前员工身份来拦截；本例不提供独立登录、假账号或真实员工授权工具。`/readyz` 仅供内部进程检查，不在菜单公共目录中。
- 固定复制的公司菜单校验模块来源和哈希见 `sdk/UPSTREAM.json`。它不处理业务数据过滤；本人记录范围由本应用的 SQL 独立实现。

## 本地验证

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm test
```

测试只启动本机隔离的临时 PostgreSQL，不读取 `.env`，不连接公司数据库。后端测试通过真实 HTTP 验证两个菜单、本人保存／查询／汇总、禁止伪造创建人、撤权、文件异常及目录错配。浏览器通过虚构身份请求头和测试中替代的网关权限端点操作真实业务 HTTP 接口与临时数据库，验证保存、刷新保留、菜单显示、旧链接拒绝、撤权及 503 后清除内容。

测试身份仅在 `tests/` 中，生产入口不会注册测试登录或身份回退。本机自动化通过不等于正式网关、真实员工扫码或业务验收通过。

## 正式验收步骤

1. 创建新的测试应用并发布此分支的固定提交，确认只使用新库，runtime 无公网直连入口。
2. 获准“验收登记”的员工保存一条测试记录，刷新后仍存在；直接访问 `/reports` 和 `/api/reports` 被拒绝。
3. 只获准“汇总查看”的员工能打开汇总，不能打开登记页或直接调用登记接口。其本人没有记录时，汇总为 0。
4. 同一员工增加“汇总查看”后，重新检查权限，能看到两个菜单及本人的记录数；另一员工看不到其记录或汇总。
5. 已登录员工撤销菜单后，重新检查或继续请求，旧链接与对应 API 被拒绝，页面清除已加载内容。停用员工后，验证正式网关对其原会话的后续请求拒绝。

本分支交付代码及自动化证据。应用创建、正式发布和员工授权由发布平台执行并另行核验；源码提交或草稿 PR 不代表应用已经发布。
